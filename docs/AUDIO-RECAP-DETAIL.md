# Audio recap detail and regeneration

On an Audio meeting page, select Short, Medium or Long, optionally enter instructions, and choose **Regenerate from confirmed transcript**. New transcript edits must be saved and confirmed first. Confirming a transcript also uses the selected level and instructions. Generation does not rerun ASR.

Short is the concise baseline. Medium targets roughly 50–60% more detail; Long roughly 100–150% more. Source density determines actual length. Sparse meetings must not be padded. An overly wordy complete meeting recap can receive one optional wording-refinement pass; intermediate batches are not rewritten for style. The denser alternative is accepted only after complete coverage validation; if refinement fails, the complete draft is retained. No draft is cut or padded by word count. Each source chunk receives the level-specific coverage instructions and approximate source-proportional length guide, with output budgets of 2,400 / 3,840 / 6,000 tokens. A bounded repair increases the output budget without falling back to a 250-word summary. Attendee/title cues are omitted from model context; names cannot be attached to anonymous source statements merely because they appear in the attendee list. Confirmed speaker tags and explicitly named source facts or review notes remain usable evidence.

The full included reviewed transcript is divided into bounded UTF-8-budgeted requests under a 16–32K configured context. Every source chunk must complete successfully. Its thematic paragraphs and bullets become individually identified coverage units for consolidation. The consolidation schema returns sections with explicit topic IDs and text; the backend validates complete coverage. Small omissions are filled directly from the complete saved source-topic paragraphs; larger omissions, unknown IDs or duplicates trigger a bounded repair and fail without publishing if still invalid. Working-note headings are attached to their content rather than counted as independent facts. It never truncates source notes to fit the context. Oversized inventories are packed into bounded consolidation batches; every batch must cover its complete inventory. A final meeting-wide pass reconciles the validated parts when they fit safely, again checking the complete original topic-ID set. If that additional pass cannot fit, the validated parts are retained and the context limitation is recorded. Completed source stages remain cached for recovery.

The final recap is thematic, rather than a concatenation of lengthy working notes. Its source-proportional word guide retains the concise Short baseline, with multipliers of 1.55 and 2.25 for Medium and Long. Every level receives all source topics, and level-specific instructions change which supporting facts and technical reasoning are retained across those topics. Base output budgets are 2,400 / 3,840 / 6,000 tokens, with up to 1,600 additional tokens reserved for structural coverage IDs during consolidation. The shared context ceiling remains unchanged. Sparse, single-request sources do not undergo another summary pass and must not be padded. Coverage validation is structural: it does not prove that the model understood every fact or faithfully represented every detail. Human review remains mandatory.

The existing owner-scoped durable review queue, shared heavy slot, memory admission and Traffic Control remain authoritative. Progress shows source stages; request/response captures, completed-stage cache and retry survive failure or process restart. Cache fingerprints include the actual model metadata, source, instructions, level-specific prompt and output budget. A new regeneration is a new attempt; retry reuses successful stages of the failed attempt. Original audio/transcript and earlier revision files are untouched.

The generated recap becomes a new immutable **unapproved draft**. Review and edit it, save edits as another immutable revision if needed, and approve the exact desired revision separately. The previous approved snapshot remains eligible and indexed until replacement approval and the existing nightly approved-only ingestion. Regeneration never calls Knowledge ingestion or changes its ledger. Withdrawal remains in force across generation and approval; only explicit restore can permit reingestion. Owner checks, stale-revision checks and pending-task locks apply on the backend.

Optional instructions are not copied into revision feedback/history, recap metadata or Knowledge source text. They remain in the private task payload and generation request archive for durable retry and diagnostics, alongside other private source data. The field clears after generation submission and when switching meetings. Saving a transcript draft retains unsent instructions in the current page; retry uses the saved generation settings, while Regenerate applies new settings. This is **private recovery retention**, not an ephemeral/no-storage input. Do not put secrets in presentation instructions. The model may incorporate a requested presentation change in the draft itself; review that draft before approval.

## Rollback

Deploy only the eight runtime files listed in the release manifest, after all user processing and staged evaluations release the heavy slot. Verify production baseline fingerprints before replacing any file. Back up those files and SQLite state first. No schema migration, model/config changes, ingestion change or Open WebUI Function replacement is required.

Use the guarded deployment helper with `--rollback BACKUP_DIRECTORY` to restore only the runtime files, then restart the idle worker and check `/health`. Leave the databases, immutable revisions, approvals, withdrawal state, ingestion ledger and source archive in place. Restoring a database snapshot during routine code rollback would discard subsequent user work and is deliberately excluded. Existing queued tasks contain backward-compatible transcript payloads; the previous generator ignores the new detail options and would generate its old concise form, so finish or cancel new waiting tasks before rollback where practical.

## Large-inventory coverage recovery

If a consolidation and its bounded repair both return invalid coverage, inventories larger than 24 topics fall back to disjoint groups of at most 24 original saved topic records, also packed within the context budget. Each group must independently pass the same exact-coverage checks and its own bounded repair. Unknown or duplicate IDs are never accepted, and no marker is removed merely to make validation pass. Smaller invalid groups still fail safely; successful source and consolidation stages remain cached for retry.

Validated groups are retained together as the draft. The partition cache records that fallback was required; a partitioned meeting-wide result is not labeled globally reconciled, including on cache reuse. Optional style refinement is skipped for that partitioned result, avoiding another lossy pass over the same oversized ID inventory. Human review must reconcile any remaining cross-group repetition or source qualifications.

The recovery regression reproduces missing and duplicate markers in large merges, verifies smaller disjoint groups preserve their complete inventory, rejects invalid small groups and checks repeat cache reuse. The full review/dashboard/deployment suite passes 206 checks.

## RAM-aware admission and recovery

The Audio guard uses Linux MemAvailable, the installed model size and its full/sliding-attention cache layout. Normal generation prefers the configured 32K ceiling. On the deployed Gemma layout, measured f16 KV buffers total about 1,152 MiB at 32K; 16K saves only about 256 MiB. The guard therefore does not assume every sliding-attention layer allocates a full 32K cache. A fresh-load estimate includes model weights, architecture-derived KV, 1 GiB runtime/workspace and a 2 GiB headroom target. An already resident model at the selected context only needs the headroom check. This is a practical admission estimate, not an exact process-RSS forecast.

A new attempt uses 16K only if the preferred context does not fit and all instructions plus a safe source-input budget still fit. Short/Medium/Long output budgets remain unchanged; the full transcript is packed into more bounded chunks rather than cut. The chosen context is persisted. Resuming an existing cached attempt retains its context and waits for headroom instead of invalidating completed stages unnecessarily. The shared heavy slot remains in force. Audio recaps use their own admission guard rather than being held by an unrelated 8 GiB startup threshold when the model is already resident; ASR, Notes and Research retain their previous gates.

Admission is checked before each model request/retry. Available RAM is sampled during streamed generation alongside bounded partial captures. A brief dip below the 2 GiB target is tolerated; sustained pressure over two samples or less than 1 GiB available pauses inference. Completed-stage caches and partial output remain saved, the recap model is asked to release its allocation, and the same task returns to the durable queue with a 60-second retry interval. Traffic Control shows the RAM wait. It is not marked failed and does not send a failure notification. Previous revision/approval/withdrawal state remains intact. Low RAM during optional wording refinement keeps the already complete draft.

The guard is enabled by default. RECAP_RAM_HEADROOM_MB defaults to 2048 and is bounded to 1024–8192 MiB. SMARTINIS_RECAP_RAM_GUARD=0 is an operator diagnostic opt-out; it restores the older shared startup admission behavior. RAM/model-status uncertainty pauses safely. Source and Knowledge retention are unchanged; this is not a disk-cache deletion policy.

Validation covers preferred 32K versus adaptive 16K, measured Gemma KV sizing, transient/critical pressure, stream interruption, full-source coverage at every detail level in an 85-minute fixture, cache resume, durable queued waits, unchanged approvals, scheduler isolation and code-only rollback including removal of the new module. The review suite passes 222 checks. Real-model synthetic checks verify normal 32K Long and bounded 16K Short with corrections/exclusions, without modifying real meetings or running ASR.

RAM-paused attempts in their retry interval are excluded from ready-work selection. Other ready Notes, audio and recap jobs can proceed; the scheduler scans only small queue metadata rather than loading every transcript payload. A dedicated fairness test verifies that a paused recap does not block ready Notes.
